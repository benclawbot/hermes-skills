# PM Skill: Sprint Review (pm-210)

The sprint review is the team's moment to demonstrate value delivered. It is a collaborative event where the team shows completed work to stakeholders, gathers feedback, and determines what is done versus not done. It is NOT a status meeting — it is a demonstration and dialogue.

## When to Use This Skill

- At the end of each sprint (mandatory)
- When stakeholders need to see working software/ deliverables
- When acceptance criteria need formal validation
- When product direction needs stakeholder input
- Before sprint retrospective (review must come first)

## Workflow

### 1. Pre-Sprint Review Preparation

**Team Preparations** (1-2 days before):
- Verify all completed stories meet Definition of Done (DoD)
- Prepare demo environment (staging, test, demo data)
- Rehearse demos if presenting complex functionality
- Ensure demo is runnable without team member "heroics"
- Assign demo narrators (not necessarily the developer who built it)
- Prepare a "not done" summary for stories not completed

**Facilitation Preparations**:
- Book room or video conference (with recording)
- Invite all stakeholders (product, business, sponsors, QA)
- Set agenda and timebox
- Prepare feedback capture mechanism (physical board, digital form)
- Confirm Product Owner attendance (required)

### 2. Sprint Review Agenda

**Duration**: 1-2 hours for a 2-week sprint

| Time | Topic |
|------|-------|
| 10% | Welcome, sprint goal reminder |
| 60% | Demo completed stories |
| 15% | Review not-completed stories and rationale |
| 10% | Gather stakeholder feedback |
| 5% | Close and next sprint preview |

### 3. Conduct the Sprint Review

**Opening (5-10 min)**:
- State the sprint goal
- Remind attendees what was committed
- Set expectations: this is a demo and dialogue, not a status report

**Demonstrations (50-60 min)**:
- Demo each completed story
- Walk through acceptance criteria one by one
- Show the actual working deliverable (not screenshots unless demo isn't possible)
- Narrate: What was built, how it works, what problem it solves
- Pause for questions after each story or at natural breakpoints
- Mark each story as: Accepted | Rejected | Needs Clarification

**Demo Best Practices**:
- Demo end-user behavior, not implementation details
- Use realistic data (not "test", "asdf", "xxx")
- If demo fails: acknowledge it, note it, don't fake it
- Keep technical jargon minimal for business stakeholders

**Not-Completed Stories (10-15 min)**:
- List stories that were not completed
- Explain why (scope was too large, unexpected blockers, priority shift)
- Be transparent — stakeholders appreciate honesty
- Note whether incomplete work rolls to next sprint or is re-prioritized

**Feedback Collection (10 min)**:
- What worked well from the stakeholder perspective?
- What concerns do stakeholders have?
- Are there new requirements or changes based on what they saw?
- Is the product direction still aligned with business needs?

**Close (5 min)**:
- Thank stakeholders for attendance and feedback
- Preview next sprint's goal and key deliverables
- Confirm date for next sprint review

### 4. Story Acceptance/Rejection

**Acceptance Criteria Must Be Met**:
- Story is accepted only if all acceptance criteria are satisfied
- If criteria are partially met: reject or mark "conditional accept"
- If environment/demo fails but criteria are met: accept with note

**Rejection Handling**:
- Rejected stories return to product backlog
- PO determines re-priority and whether it goes in next sprint
- Root cause of rejection should be captured
- Do NOT let rejected stories languish in "completed" column

**Conditional Acceptance**:
- Use sparingly when minor tweaks needed
- Define exact changes required
- Assign owner and timeline for fixes
- Stories with conditional accept should be re-reviewed before sprint closes

### 5. Feedback Integration

**Post-Review Actions**:
- Triage feedback into:
  - **New stories** (new requirements) → backlog
  - **Scope changes** → PO re-prioritization
  - **Defects** → backlog with priority
  - **Direction changes** → strategic discussion with PO/sponsor
- Update product backlog with new or changed items
- Communicate outcomes to stakeholders within 24 hours

### 6. Documentation

**Sprint Review Record**:
- Date, attendees, apologies
- Stories demonstrated and acceptance status
- Feedback themes identified
- New or changed requirements
- Sprint review recorded (video or written summary)

## Common Pitfalls

- **Status report in disguise**: Just showing slides instead of working demos
- **No stakeholder participation**: Monologue without dialogue
- **Skipping rejected stories**: Pretending everything is complete
- **Demo failures**: Unprepared demos waste stakeholder time
- **Not recording**: Valuable feedback lost without a record
- **Accepting without validation**: Accepting stories that don't meet criteria

## Verification Steps

1. Sprint review held within 1-2 days of sprint end
2. All completed stories demoed with working software/deliverables
3. Stakeholder feedback captured and triaged
4. Stories accepted/rejected/conditional documented
5. Not-completed stories documented with rationale
6. Product backlog updated with new feedback-driven items
7. Sprint review summary communicated to stakeholders

## Tools

- Demo environment (staging, test server, demo instance)
- Sprint board for story status reference
- Feedback capture form (physical or digital)
- Meeting tool with recording capability
- Product backlog (updated post-review)
- Sprint review summary template

## Exit Criteria

- Sprint goal reviewed with stakeholders
- All completed stories demonstrated and accepted or rejected
- Stakeholder feedback captured and triaged
- Product backlog updated
- Sprint review summary distributed
- Action items from review assigned and tracked
