# Vault Analysis → Structural Fix Patterns

Captured 2026-06-02 from the Memory vault session. After the initial
`vault-pattern-mining` analysis surfaced 7 themes, the user asked for
each theme's "What the vault would need to look different" recommendation
to be implemented as actual structural changes. Three fixes happened
(theme 05, theme 07, and the meta-finding), and a repeatable pattern
emerged.

## The 3-layer model for vault fixes

When a theme says "the vault should do X", map the fix to the right layer.
Pick the highest layer that fully addresses the issue — code-level fixes
that prevent the bad data from being written in the first place are
better than content-level fixes that clean it up after.

### Layer 1 — Skill / script

The fix lives in the code that generates the data. Re-running the script
on existing data retroactively fixes the corpus, AND prevents new bad
data from being created.

**Example (theme 07, Empty Containers):**
The empty conversation files were caused by `save-session-to-obsidian`
writing only timestamps and topics — never decisions. Fix:

```python
# In scripts/watch_sessions.py — added detect_decisions()
def detect_decisions(messages):
    """Heuristic detection of first-person commitments and
    switch/decide verbs. Capped at 5 per session."""
    ...

def write_to_obsidian(date, summary_text, session_file=None):
    ...
    if filepath.exists():
        with open(filepath, "a") as f:
            f.write(content)
    else:
        with open(filepath, "w") as f:
            f.write(f"# Conversation — {day}\n{content}\n\n---\n"
                    f"## Decisions today\n"
                    f"_(Auto-detected from this day's sessions. "
                    f"Edit to keep only what was actually decided.)_\n")
```

**When to use:** The bad data is being generated by a script/process
that you can modify. Retroactive fixing is a free side effect.

**When NOT to use:** The data was generated by a one-off action
(manual write, past import, etc.) and no ongoing process will keep
adding more bad data.

### Layer 2 — Frontmatter / metadata

The fix is a one-shot migration of structural metadata, plus a maintained
reference for future values.

**Example (theme 05, Tag Explosion):**
1,585 unique tags, 77% singletons. The same concept was written
`#semiconductors`, `semiconductors`, `#semiconductor`, `#concept/semi-conducteurs`.
Fix:

1. Build a canonical reference at `AI/skills/<topic>/REFERENCE.md`
   (87 forms, 132 aliases, 2 type markers to drop)
2. Build an idempotent migration script that rewrites notes
3. Re-run the analyzer to confirm the diagnosis has cleared
4. Update `AI/vault-map.md` and `AI/me.md` to enforce the policy

**When to use:** The bad data is in frontmatter/metadata, not body
content. The fix is a one-shot rewrite + ongoing convention.

### Layer 3 — Content

The fix is a one-shot rewrite or delete of the bad data, with no
ongoing process to maintain. Examples: delete the empty broken-format
files, rewrite 35 broken wikilinks.

**When to use:** The bad data is leftover from an older process that
no longer runs, and the canonical path now exists with the correct
content.

**Pitfall:** If you ONLY do layer 3 without layers 1 or 2, the same
bad data will regenerate. Always close the loop.

## The idempotency rule for migration scripts

**A well-written migration script run twice produces the same final
state as run once.** This is verified trivially:

```bash
# First pass
python3 migrate_tags.py --apply
# Expected: 358 files changed, 909 changes

# Second pass (immediately)
python3 migrate_tags.py --apply
# Expected: 0 files changed, 0 changes
```

If the second pass reports any changes, the script is non-idempotent
and will re-corrupt data on every run. The most common cause: the
change-detection logic compares the *normalized* form to the canonical
form (always equal after first run), not the *visible* form.

**Pattern for idempotency:**

```python
# Wrong: compares normalized form, never re-records change
if normalize_tag(t) != rewritten:
    changes.append(...)

# Right: compares raw (visible) form to canonical, so any visible
# difference triggers re-rewrite
if raw != rewritten:
    changes.append(...)
```

The second-pass output should report `Files changed: 0, Total changes: 0`.
Anything else is a bug.

## The verification pattern: re-run the analyzer

The proof that a fix worked is that the original diagnosis no longer
fires. Re-run `scripts/analyze_vault.py` and check the corresponding
metric:

| Theme (2026-06-02) | Diagnosis signal | Post-fix signal |
|---|---|---|
| 05 Tag Explosion | 1,585 unique tags, 77% singletons, 35 files with `#` in tag list form | 1,403 unique tags, 67% singletons, 0 files with `#`, 0 type markers |
| 07 Empty Containers | 17 files with `Log: [empty]` template | 0 files (deleted); 4 broken files removed from old flat path |
| 02 Bilingual Architect | 335 YAML parse errors (broken inline `[#tag]` form) | 28 YAML errors (all pre-existing, unrelated to tags) |

The diagnosis signal must DROP. If it stays the same, the fix didn't
work — re-check Phase 7.1 (did the fix actually address the prescriptive
section?).

## The empty-container meta-finding

Theme 07 surfaced a meta-finding that the user explicitly asked to
capture as a vault note. The pattern:

1. The analysis observes a failure mode in the corpus
2. The failure mode is itself a description of how the writer
   interacts with their own system
3. The fix is a vault note that says "here is what we found, here is
   what we did about it, here is the operational rule going forward"

**Template for the meta-finding note:**

```markdown
# <Theme Name> — <Self-Diagnosis>

> This page is the synthesis of the full-corpus analysis —
> specifically **Theme N: <Name>**, which observed that <pattern>.
> It is the only theme that points inward at the corpus's own
> failure mode rather than outward at the work, and the recommended
> fixes are recorded here so the failure does not recur.

## What it actually meant
<rephrase the diagnosis in 2-3 sentences>

## The fix (applied YYYY-MM-DD)
Three changes, in order of leverage:
1. <layer 1 fix>
2. <layer 2 fix>
3. <layer 3 fix>

## Operational rules going forward
<the one or two rules that prevent recurrence>
```

**Why this matters:** Without the meta-finding note, the same failure
mode will recur in 6 months because the analysis-only output (Phase 5
site) is an external artifact. A vault note is part of the corpus
itself — the next session can find it via full-text search or wikilink.

## Commit hygiene

Each theme's fix is a separate commit. The commit message should
reference the theme number and the prescriptive section it implements:

```
vault-tags: migrate 358 notes to 87 canonical forms (analysis theme 05)
vault: empty-containers fix + Decisions section (analysis theme 07)
```

This makes the connection between diagnosis and cure explicit in the
git log. Future sessions looking at the history can see the pattern
"analysis surfaced X, then a structural fix landed."

## Pitfalls observed in the 2026-06-02 fix passes

| Pitfall | Symptom | Fix |
|---|---|---|
| Type marker detected as a tag | `#concept` / `#research` show up as content tags | Add to the drop set in the canonical map; auto-removed on migration |
| Change-detection compares normalized form | Idempotency check shows 0 changes on first pass, but `#` chars remain | Compare raw (visible) form, not normalized form |
| Symlink to script outside `~/.hermes/scripts/` | Cron tool rejects with "must live in ~/.hermes/scripts/" | Use `ln` (hardlink), not `ln -s` (symlink) — symlinks are followed by the path-resolves-into-scripts-dir check |
| Broken YAML `[#tag, #tag]` not parseable by PyYAML | Migration script silently skips the file | Special-case the parse: split on `#` and keep what comes AFTER the first `#` (the actual tag value) |
| Frontmatter schema drift (English vs French) | Single-schema parser loses half the corpus | Use the `FIELD_ALIASES` dict approach in `analyze_vault.py` — treat `title`/`titre`, `strong_links`/`liens_forts` as the same logical field |
| Stale git state during fix | `git stash` + `git commit` interactions leave untracked files in the wrong state | Commit BEFORE the migration, not after, so the fix can be `git diff`'d against a known-good commit |
