### Round 3 — fix the pre-existing bugs I rationalized as out-of-scope

After Thomas called out that I was bypassing pre-existing issues, I audited the four bugs I'd initially proposed-as-skip:

- **Integer overflow (mode #8) — REAL BUG, fixed.** `_coerce_number` was routing integer-typed fields through `float()` then `int()`, silently corrupting `99999999999999999999` to `100000000000000000000`. Fix: try `int()` first for `integer_only=True` fields, fall back to float for `"3.0"`-style decimals.
- **Boolean "1"/"0" (modes #14/#15) — REAL BUG, fixed.** Same as Round 1 above.
- **String "null" in non-nullable string field — NOT A BUG.** I probed and discovered the existing system handles it correctly. The `_schema_allows_null` check already handles the nullable case; the non-nullable case passes the literal "null" through, which is the right behavior (the model said "null" — we pass "null").
- **Null stripping on optional fields — NOT A BUG.** Same reasoning: tools with sensible defaults already handle `None`. Stripping would conflate "omit" with "empty list".

This is a useful reminder: not every "I think this is broken" claim is real. Probe before fixing. The user is paying for the *audit* — the probe is part of the deliverable.

## The 3-step verify protocol

When a session-summary claims work is done, here's the exact protocol to verify (positive form, not just the trap-table warning):

```bash
# 1. Working tree state — must show modified or staged files
git status

# 2. Change size — must be non-zero
git diff --stat

# 3. Spot-check the named files — must show actual patches
git diff -- <file-from-summary>
```

If step 1 is clean (no modified files) and the prose claims a fix was shipped, the work is un-shipped. Re-apply, don't trust.

If step 2 shows zero changes, the work is un-shipped (a no-op diff is not a fix).

If step 3 shows the wrong file or the wrong change, the work is mismatched (the patch landed in the wrong place, or the summary got the file name wrong). Recover the work from the worktree or branch the prior session was on.

## The PR-porting protocol

When a mature open-source fix exists upstream (in the same repo or a neighbouring one), adopt its contract verbatim. The key insight: a mature fix already encodes the edge cases the original author hit, and matching the contract makes the future merge conflict-free.

The protocol:

1. **Function name** — copy exactly. If the upstream is `_split_concatenated_tool_call_arguments`, name yours `_split_concatenated_tool_call_arguments`. Don't rename to `split_tool_call_args` because it's "cleaner."
2. **Signature** — copy the parameters, defaults, and return type annotation. The "None vs list" semantics in particular are usually load-bearing.
3. **Return shape** — copy. If the upstream returns `Optional[List[str]]`, yours should too. Don't return a dict or raise exceptions just because your local style prefers it.
4. **Test cases** — copy. The upstream's test grid is part of the contract. If they test that `"partial tail"` returns `None`, you should test the same thing.
5. **Module location** — match where you can. If the upstream puts the helper in `agent/transports/content_tool_calls.py`, putting it in a different module just creates a small re-import when the PR merges.

The cost of matching the contract is zero (you'd write the code either way). The benefit is a near-zero-conflict merge when the upstream lands. The cost of *not* matching is having to re-port later, which is more work than doing it right the first time.

In this session, `_split_concatenated_tool_call_arguments` was adopted verbatim from PR #25346. The PR [#38042](https://github.com/NousResearch/hermes-agent/pull/38042) opened at the end of the session will merge with the upstream PR whenever #25346 lands, with essentially zero conflicts.

## The "two helpers, complementary not competing" design decision

This is a design decision worth recording because it was *not* obvious and the wrong design (using just the extractor) would have silently eaten data.

Two failure-mode classes:

- **`_split_concatenated_tool_call_arguments`** — payload is 2+ complete top-level dicts with no delimiter. The model emitted *multiple parallel tool calls as a single chunk*. The split helper returns a list of re-serialised JSON strings.
- **`_extract_first_json_object`** — first JSON value parses but the trailing text does not. The "valid + garbage" pattern. The extract helper returns the first complete dict, discards the rest.

The two are complementary: split handles the "all dicts are real" case, extract handles the "first dict is real, the rest is junk" case. They use the same primitive (`json.JSONDecoder.raw_decode()`) but with different return contracts (list vs single).

**The critical ordering rule:** the split MUST run before the extract. If the extract runs first, it returns the first dict and the second dict in `{"a":1}{"b":2}` is silently lost. The split correctly returns both, and the streaming-integration seam in the calling layer (or the per-call repair path, in our case) handles each one separately.

The current implementation in `_repair_tool_call_arguments` returns only the first split element (since the single-call repair path doesn't have the streaming context to fan out). The full list is available for the streaming-integration seam when it lands.
