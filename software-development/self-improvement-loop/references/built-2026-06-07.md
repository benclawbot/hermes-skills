**The "wire the digest" lesson (now in `cronjob-ops`):** when
auditing "is this cron job wired?", trace the prompt's
`python3 <script>.py` reference to a real function, confirm that
function is invoked, and **test by running the script directly**
(`source ~/.hermes/.env && python3 <script>`), not by triggering
the cron. A job that was never actually wired up will never have
run, so there's no "previous status" to check — `last_status: ok`
is from a stale read, not a real run.

**Repo rename — 11 surfaces swept, not 1:**

A rename is a rename of a *system*, not a directory. The folder
is one touchpoint out of a dozen. Touchpoints that needed updating:

| Surface | Tool used |
|---|---|
| GitHub repo name | `gh repo rename` (only path that updates redirects) |
| Local dir | `mv` |
| `git remote` URL | `git remote set-url` |
| `README.md` | `patch` (7 path refs) |
| `src/db.py` docstring | `patch` |
| `tests/test_branch_full.py:274` | `patch` (`cwd=` for subprocess.run) |
| `scripts/run_cycle.sh` | `patch` (`cd` path) |
| 3 cron shell scripts (`sri-propose/judge/cycle.sh`) | `patch` (`cd` paths) |

| `~/.hermes/memories/MEMORY.md` | `patch` (path in schema-migration note) |
| 3 live-path skill docs | `patch` (live path pointers in `sri-cycle-split.md` etc.) |

**The audit pattern — 4 phases, in order:**

1. GitHub + filesystem (visible surface)
2. Inside the repo (`git grep` finds these)
3. Outside the repo (cron DB, env files, agent memory, hub-installed skills, machine config) — **don't trust `git grep` alone, it misses all of this**
4. Test pass — the integration test is the canary

The `test_branch_full.py:274` `subprocess.run(..., cwd="/home/thomas/self-recursive-improvement", ...)` was the canary
that crashed first and forced the rest of the sweep. The cron
jobs would have silently run with stale `workdir` for weeks.

**The "live path vs historical record" rule:**

| Reference | Live or historical? | Action |
|---|---|---|
| `cd ~/old-dir/ && python3 src/x.py` in a recipe | Live | Update |
| `~/old-dir/docs/spec.md` in a "see also" pointer | Live | Update |
| `git log ef78713` quoting a past commit | Historical | Leave |
| `learned 2026-06, old-name session` in prose | Historical | Leave |
| `data/backups/20260607_old-dir_*` listing a past artifact | Historical | Leave (the backup IS the old path) |
| `last_status: ok` referencing a deleted run | Historical | Leave (log content) |

The rule: **if following the reference would take you to a
non-existent place, update it. If it points at a past fact
(a backup, a commit, a session), leave it.**

**The fix for the `cwd=` rename-bug pattern (now in
`codebase-porting` and `test-what-you-built`):** every test that
spawns a subprocess or references a project path should derive
from `Path(__file__).parent.parent`, never hardcode the dir name:

```python
# WRONG — breaks on rename, on clone, on move to a different machine
r = subprocess.run(["python3", "src/apply.py", "--revert", cid],
                   cwd="/home/thomas/some-dir", ...)

# RIGHT — derives from the test file's location
PROJECT_ROOT = Path(__file__).parent.parent
r = subprocess.run(["python3", "src/apply.py", "--revert", cid],
                   cwd=PROJECT_ROOT, ...)
```

A test that hardcodes an absolute path is a latent rename-bug
waiting to fire. `tests/test_branch_full.py:274` is the
worked-example ref; the rewrite is `Path(__file__).parent.parent`.

**Migration order bug — found during the rename audit:**

After the rename was complete, ran `tests/test_pipeline.py` to
verify "nothing broke." It failed on a fresh DB with
`sqlite3.OperationalError: table proposals has no column named
propose_ms`. The bug is described in detail in SKILL.md under
"**Migration order bug, round 2 — silent column loss on fresh
DBs (verified 2026-06-07)**." The fix (commit `cc44d42`) added
the migrated columns to the `CREATE TABLE` in SCHEMA while
keeping the `_MIGRATIONS` ALTER statements as a backstop for
already-deployed DBs. Both test suites now pass: 12 pipeline +
47 branch = 59 green. Prod DB unchanged.

**Implication for the loop:** any new contributor who adds a
migration must (a) add the column to SCHEMA's CREATE TABLE too,
(b) update the canary probe in the verification checklist, (c)
test against a fresh DB, not just prod. The pre-existing bug
existed for 8+ hours of the loop running before the audit
caught it. The cost of a 5-line probe on every PR is much
lower than the cost of silent column loss.
